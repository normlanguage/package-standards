# Norm 包与仓库规范

适用于 `normlanguage` 下的代码仓库。包命名、模块边界和 NAR 发布规则适用于对外发布的库；应用、编译器、工具和基础设施仓库遵循各自交付方式。

规范要求必须可以验证。不创建没有内容、使用者或维护价值的占位文件。

## 1. 仓库、模块和源码包

仓库是源码维护边界，Module 是依赖、版本和发布边界，package 是源码命名空间。一个 Module 可以包含多个 package。

一个库仓库拥有一个对外发布的 Module。测试、示例可以有自己的本地模块，但不作为第二套公共库发布。

独立发布的库必须有实际消费者、公共 API 和维护边界。仅供一个库内部使用的绑定、适配器和实现层保留在库内；不为目录分类或单个实现文件建立发布模块，也不为减少仓库数量而合并独立职责。

## 2. 仓库和模块命名

正式库仓库名与 Module 名完全一致，使用小写、点分层名称，例如 `ui`、`ui.theme`、`ui.fx`、`ui.web`、`ui.fx.kit`、`micronaut.inject`、`orm.hibernate`。

- 不将点转换成连字符。
- 不添加无信息的 `norm-`、`-norm`、`-lib`、`-package` 或版本后缀。
- 不照抄 Maven 坐标构造重复名称，例如 `jsoup.jsoup`。
- `core`、`base`、`common`、`util` 必须有明确职责，不作为杂物包。
- 已有上游正式名称可以保留，例如 `org.json`。

应用和工具可保留正式产品名称。`awesome-norm`、`homebrew-tap` 等非库仓库不受同名规则约束。

## 3. 名称与依赖层次

通用协议按领域命名，协议实现放在协议之下，后端组件库继续细分。独立第三方绑定按上游库命名。

点分层不隐含依赖、导出或自动加载，实际关系必须由 Module 声明。每一种公共类型只有一个定义来源，工具链已有的标准类型不在外部包重复绑定。不发布同内容的别名模块。

## 4. UI 职责边界

| 模块 | 职责 |
| --- | --- |
| `ui.theme` | 颜色衍生、主题模型和主题变化 |
| `ui` | 通用组件协议、布局、状态、生命周期和配置 |
| `ui.fx` | JavaFX 类型绑定及通用协议的 JavaFX 实现 |
| `ui.web` | 通用协议的 Vaadin 实现 |
| `ui.fx.kit` | JavaFX 具体组件和交互行为 |

JavaFX 绑定由 `ui.fx` 统一拥有，不提供独立的 `javafx` 发布模块。其他组件库通过 `ui.fx` 的明确公共入口使用相关类型。

通用协议不能依赖具体后端。组件库发现通用能力缺口时，补充协议和后端实现，不另建一套基础能力。

库不默认占用应用固定路由、全局启动配置或应用外壳。示例专用容器、展示资源和服务器配置归示例所有。

## 5. 公共 API

`exports` 只包含承诺维护的 API。内部绑定必须通过模块可见性隔离；声明名称与可见性独立表达，不根据导出列表的位置推断类型名称。

确有需要的原生扩展设计为稳定的公共能力，应用不依赖内部适配器。示例主要使用公共 API，不能靠内部入口证明公共 API 完善。

每个领域行为只有一个实现来源。例如表单状态、校验、重置和提交不能分别在 Java 与 Norm 维护。

## 6. 仓库结构

| 位置 | 内容 |
| --- | --- |
| `README.md` | 项目说明和使用入口 |
| `LICENSE` | 自身代码的许可证正文 |
| 模块目录中的 `module.norm` | 唯一模块声明 |
| 模块源码与测试目录 | 实现与模块测试 |
| `samples/` | 独立消费者示例 |
| `docs/` | 无法由源码或 README 承担的唯一说明 |
| `scripts/` | 人和 CI 共用的必要开发入口 |
| `.github/` | 持续集成和协作配置 |

有实际内容才创建目录。Norm 源码遵循模块路径规则，宿主语言源码遵循对应构建工具的标准目录。

构建结果、缓存、日志、临时截图和本地配置不得混入源码目录或提交。确需提交的生成物应有唯一生成入口和一致性验证，不能人工维护第二份源码。

## 7. README

README 必须说明用途和边界、获取和运行方式、最小真实用法、平台与工具链要求，以及示例、开发、文档和许可证入口。

- 标题使用正式项目或 Module 名，开头简要说明用途。
- 库提供真实依赖声明和最小用法；应用提供安装、启动方法。
- 快速开始可以复制执行，不省略必要步骤，不使用虚构 API 或个人路径。
- 区分稳定版本用法与主分支开发，支持范围如实说明。
- 完整 API、依赖和长篇架构说明使用链接，避免重复维护。
- 徽章必须反映真实状态。

可执行片段优先引用经过验证的示例；直接写在 README 中的代码也必须检查或执行。

`README.md` 为英文入口，`README.zh-CN.md` 为中文入口并相互链接。二者使用相同事实来源和章节职责，不定义不同 API 或支持范围。

## 8. 示例

每个库至少提供最小示例。综合示例不能成为唯一入门方式。

示例必须用途清晰、入口完整、依赖明确，能从独立目录和干净环境运行，正确处理启动、关闭、取消和资源释放。只使用可公开分发的数据，不包含个人配置或真实凭据。

普通示例默认使用发布包。源码联调是显式开发模式，不要求使用者准备同级仓库；不依赖隐含缓存、手工文件、绝对路径或预启动进程。外部服务需要可复现的准备方法与配置入口。

展示源码、页面内容、截图和测试夹具不进入库运行产物。UI 示例展示有效内容、主要状态和真实交互，不用占位页面证明组件已实现。

## 9. 文档

README 负责发现和开始使用；API 以源码为准；docs 保存概念、约束与操作流程；示例提供可运行用法；GitHub Release 保存交付记录和必要迁移说明。

不复制依赖表、版本表、组件清单或发布步骤。文档必须能从入口索引到达，失效链接、过时示例和旧说明随代码清理。翻译同步事实，不建立不同规范。临时调研和工作日志留在临时目录。

## 10. 许可证和资源来源

本规范仓库及 Norm UI 模块采用 MPL-2.0。其他仓库保留已确定的许可证；新增选择或变更由负责人决定，不由模板推断。

根目录提供正式 LICENSE 正文，README 链接该文件，适用的构建元数据使用一致的 SPDX 标识，发布产物携带许可证。许可证保持 UTF-8、LF 换行；生成副本由构建从根文件产生，不独立维护。资源路径按模块身份区分，避免多个依赖的同名文件冲突。执行规则见 [registry 打包入口](https://github.com/normlanguage/registry/tree/main/.github/actions/package-module)。

随包分发的第三方源码、字体、图标、图片等保留其要求的许可证和署名，按实际内容集中维护 THIRD_PARTY_NOTICES 或上游要求的 NOTICE。普通依赖声明与实际复制分发区分处理；不能将依赖图笼统声明为仓库许可证。

发布前解决许可证缺失、矛盾和资源来源不明问题，自动化不得猜测补全。

## 11. 元数据和构建

module.norm 是名称、版本、依赖、导出和绑定指纹的唯一声明来源。注册表只记录拥有关系，不复制版本和依赖；标签、资产名及可派生构建信息从声明生成或校验，不增加重复清单。

库 JAR 不包含示例源码、文档展示资源与测试夹具。开发命令由明确入口承载，README 与 CI 复用。工具链、编码和环境要求显式声明。

普通构建、测试和示例运行不能改写声明或重新接受指纹；只有明确更新操作可以修改依赖与指纹，并经过代码审查。

## 12. 发布

库版本采用正整数，模块版本 5 对应标签 v5。已经发布的版本、标签和资产不可覆盖或重用，改名不能重写历史版本。

固定工具链与依赖，保证产物可复现。共享流程维护通用打包、指纹与资产校验、发布步骤；各库只增加自身构建和验收，不复制发布实现。工具链必须可获取并明确要求。

发布记录说明交付、必要迁移和已知限制，不复制工作日志。旧库完成消费者迁移后移出活动注册入口、说明替代位置并归档，不保留转发包或双重实现。

## 13. 验收

验证公共 API、声明平台的真实运行、空缓存正式包消费，以及关闭、卸载、取消和重复挂载的资源释放。UI 额外验证主题切换、输入状态保持与关键样式。

测试从可维护的分类产生，避免手写类名列表漏项。选择性测试必须说明范围，不将部分检查通过表述为全部能力通过。README 命令、示例、文档链接和发布资产都是验收对象。

## 14. 维护入口

提供问题反馈、贡献和维护入口。组织共用贡献指南、行为准则、安全反馈和 Issue/PR 模板集中维护并复用，各仓库只补充特有要求。

需要时以 CODEOWNERS 划分实际评审责任，不填写占位责任人。仓库描述、主页、主题标签、默认分支和归档状态反映当前用途，改名和退役时同步相关入口。
